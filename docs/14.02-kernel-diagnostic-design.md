# PS4 14.02 — Diagnostic design and limitations

**Status:** Offline documentation only
**Last reviewed:** 2026-11-11
**GoldHEN 14.02 launch:** Disabled

## 1. Purpose

This document describes the scope, limitations, and historical context of the PS4 firmware 14.02 diagnostic work.

The repository contains offline diagnostic utilities and self-tests. These utilities do not establish firmware compatibility, validate exploit safety, or authorize execution on console hardware.

No successful GoldHEN 14.02 launch has been established.

## 2. Current repository components

| Component | Purpose | Limitation |
|---|---|---|
| `site/preflight-1402.js` | Classifies supplied byte ranges | Does not authenticate kernel images |
| `tools/check-1402-snapshot.cjs` | Checks a local snapshot | Does not establish hardware compatibility |
| `tools/build-guarded-bootstrap-1402.cjs` | Generates an offline prototype | Not validated for console execution |
| `site/teardown-verify-1402.js` | Checks supplied structural snapshots | Does not perform cleanup |
| `tests/` | Exercises local diagnostic logic | Does not validate console behavior |

## 3. Historical technical context

Earlier development investigated differences between the available 14.02 reference data and expected byte patterns.

The available kernel reference was found unsuitable as a pristine stock reference. Some inspected regions already contained modified or incomplete values.

Consequently, classifications produced from that reference must not be treated as proof of a genuine retail kernel state.

Earlier design notes also discussed potential kernel-state changes and cleanup concerns. Those notes are historical engineering context, not validated procedures or instructions for console execution.

## 4. Teardown verification scope

`site/teardown-verify-1402.js` is an offline verification utility.

It checks supplied snapshots for:

- Original and cloned operation-table byte patterns.
- Device and queue file-operation pointers.
- Queue note values.
- Expected close-stub bytes.
- Completeness of the supplied verification data.

A successful result means only that the supplied data passed the implemented checks.

It does not prove:

- That real device handles have been closed.
- That kernel resources have been safely released.
- That all runtime references are valid.
- That a cleanup operation is safe on physical hardware.

The self-test validates the local verification logic, not actual kernel cleanup.

## 5. Diagnostic limitations

The offline preflight examines 24 known byte ranges.

It does not:

- Authenticate the complete kernel image.
- Establish that supplied bytes originate from retail firmware.
- Prove exploit compatibility.
- Prove kernel stability.
- Authorize kernel writes or GoldHEN execution.

Snapshot classifications are byte-pattern results only.

Passing local tests is not evidence of hardware safety.

## 6. Test coverage

The repository includes offline self-tests for:

- Launch-gate state and disabled-launch behavior.
- Preflight byte-range classification.
- Guarded-bootstrap prototype logic.
- Teardown snapshot verification.

The launch-gate self-test evaluates `launch.js` in an isolated test environment. It does not load `launch.html` or its directly imported `jb-g.js` module.

Therefore, the direct `launch.html` path is not covered by this self-test and remains unverified.

The GitHub Pages workflow runs these four self-tests before deployment.

These tests validate local diagnostic and gating logic only. They do not constitute hardware validation, exploit validation, or release certification.

## 7. Safety and release status

The first reconstructed 14.02 candidate caused a hardware kernel panic.

No subsequent result has established a reliable and safe GoldHEN 14.02 launch.

Therefore:

- GoldHEN 14.02 launch remains disabled.
- No console-ready diagnostic release is claimed.
- Offline prototypes must not be represented as validated console components.
- No successful test result should be interpreted as permission to enable the launch path.

## 8. Conclusion

The current 14.02 work is an offline research and diagnostic project.

Its purpose is to document known data, classify supplied snapshots, test local validation logic, and make remaining limitations explicit.

**Firmware 14.02 compatibility and safe GoldHEN execution remain unconfirmed.**
