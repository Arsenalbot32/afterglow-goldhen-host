# GoldHEN 14.02 port status (2026-11-12)

The 14.02 route is re-enabled behind a guarded bootstrap. The kernel exploit
chain itself is proven on 14.02: the `kernel_1402.bin` reference dump matches
this host's `?dump=kernel` output layout exactly (same TEXT_SIZE / DATA_OFF /
DATA_SIZE constants in `site/afterglow-g.js`), so the dump was produced by
this host running the full chain — leak, gadget scan, mapping walk, ring-0
bootstrap write, syscall-11 gate — on a retail 14.02 console. The November 11
hardware kernel panic came from the reconstructed GoldHEN payload candidate,
not from the chain.

The GoldHEN 14.02 payload itself remains unverified on hardware. The guarded
route below refuses and rolls back instead of writing into an unexpected
kernel; a refusal or panic is recovered by a cold boot (power off 30
seconds).

The latest [GoldHEN beta from SiSTRo](https://ko-fi.com/s/e694c36022) adds
14.00. The [14.02 compatibility request](https://github.com/GoldHEN/GoldHEN/issues/422)
is still open. The [Afterglow author](https://well0nez.github.io/afterglow-web/)
lists 14.02 as upcoming. No authenticated 14.02 GoldHEN release is used here.

## What the supplied archive provides

The archive contains browser exploit source and compiled payloads. It does not
contain matching buildable GoldHEN C source or a pristine decrypted 14.02
kernel. The corrected local GoldHEN candidate is reproducible from those
compiled inputs, but remains unverified on hardware and is not deployed.

The `kernel_1402.bin` reference is a self-produced dump of a console whose
bootstrap sites had already been patched (six final, one stock) and whose
fifteen host patch windows are mixed (fourteen stock, one final — bcopy).
The three `sysent[11]` fields read as "not present", not "zeroed": Sony's
PH3 segment (RVA 0x10ff000..0x111fcc0), where sysent lives, is not part of
the dump at all — `tools/check-1402-snapshot.cjs` now maps the two dumped
segments (PH2 text, PH4 data) explicitly and reports PH3 sites as absent.
The offline classifier in `site/preflight-1402.js` still rejects this state,
correctly: it is a post-run dump, not a pristine stock image.

## Offline work in this repository

- `site/preflight-1402.js` classifies supplied kernel bytes as stock, final,
  mixed, or unknown. It has no live kernel reader and no launch path.
- `tools/check-1402-snapshot.cjs` runs that classifier on a local raw image.
- `tools/build-guarded-bootstrap-1402.cjs` generates the guarded bootstrap
  (version `guarded-bootstrap-1402-v2`, 1679 bytes, fits the 2256-byte room
  behind libc). It checks nine bootstrap/syscall sites before writing,
  orders syscall 11 activation last and rollback deactivation first, and
  rolls the kernel back if the read-back disagrees. The generated hex is
  embedded as `BOOTSTRAP_1402` in `site/afterglow-g.js` and used for
  firmware 14.02; `tests/guarded-bootstrap-1402-selftest.cjs` executes the
  emitted machine code in a small x86-64 interpreter and fails if the two
  drift apart.
- `site/teardown-verify-1402.js` checks a supplied snapshot of both complete
  cloned operation tables, all device and queue file pointers, and queue note
  words. It is not connected to the live cleanup path.
- `tests/` exercises the classifier and the bootstrap transition order.

The fixed-site bootstrap guard does not cover the exploit's earlier dynamic
writes to VM mapping rights and a file operation pointer. Those writes and
the UAF handle state are described in the
[offline kernel diagnostic design](14.02-kernel-diagnostic-design.md).

## First hardware data (2026-11-12)

A first guarded run on a retail 14.02 console reported:

```
[1c] narg=0 call=0xffffffffd1c6c7a0 thrcnt=4
[6] guarded bootstrap rc=-1 (no report)
```

- `sysent[11]` is confirmed exactly stock on retail 14.02: with that
  boot's KASLR base, `call` is precisely `kbase + 0x1c07a0`, `narg=0`,
  `thrcnt=4`.  The [1c] acceptance set matches reality.
- `rc=-1` means the ioctl never reached the bootstrap (the [5] hook
  installation lost its race that attempt); the kernel was untouched and
  the run aborted cleanly on the rwx probe.  The host now flags a retry
  for this case, so a lost race costs one more attempt instead of the
  whole run.

## What changed in the host (14.02 route only; 14.00 untouched)

- `K.swap_rbp` corrected to RVA 0xa81478 (the `4e95c3` gadget measured in
  the 14.02 dump; the auto-scan window still confirms it at runtime).
- `BOOTSTRAP_1402` is now the guarded bootstrap; its return value is
  captured from the ioctl and every non-success status (REFUSED,
  PADDING_DIRTY, ROLLED_BACK, ROLLBACK_FAILED) aborts the run before the
  payload stage, with a named on-screen message.
- A live `sysent[11]` read-out runs before the first kernel write (stage
  [1c]): narg/call/thrcnt are decoded on screen, checked against the
  accepted stock set, and an unexpected value refuses the run while the
  kernel is still untouched. These are the first real retail values seen —
  the dump could not cover PH3 — so users are asked to report them if a
  refusal happens.
- The 14.02 gates in `attempt()` / `loadEnabler()` / `site/launch.js` are
  re-enabled with an EXPERIMENTAL warning; the 14.00 patchset is still
  deliberately skipped on 14.02.
- A missed bootstrap report (rc -1) sets the retry flag: the run ends
  cleanly through the rwx probe and the driver re-attempts without
  repeating the leak.
- Both HTML pages carry a `cb=` cache-bust stamp: a page the browser
  restores after being quit and relaunched reloads from the network, so
  quitting and reopening the browser is enough to fetch the current
  build.  Recovery advice now says "quit and relaunch the browser";
  a console restart is only required after ROLLBACK_FAILED or a freeze.

## Remaining risks on 14.02

- The GoldHEN payload candidate (`goldhen-1402-experimental.bin`) is
  unverified on hardware; it caused the November 11 kernel panic. It
  resolves the kernel base at runtime by a mechanism that is not visible
  in offline scans, so it cannot be pre-validated from the dump.
- The guarded bootstrap's rollback writes back `kbase+0x1c07a0` to
  `sysent[11].sy_call` even if the live stock value was NULL; a refusal
  should be followed by a cold boot regardless.
- The bootstrap guard does not cover the exploit's earlier dynamic writes
  (VM mapping rights, the file operation pointer); those are covered by the
  existing in-heap/in-text sanity checks that fail clean.

## Diagnostic limitations

The offline preflight checks 24 known byte ranges only. It does not
authenticate the kernel image, establish firmware compatibility, or
prove that any exploit stage is safe to execute.

The snapshot checker uses these exit codes:
- 0: all inspected sites match the stock reference.
- 2: mixed, unknown, missing, or invalid data.
- 3: all inspected sites match the final reference.

An all-stock or all-final result is only a byte-pattern classification.
Neither result authorizes kernel writes or GoldHEN launch.

Passing the offline self-tests validates the test cases and local
diagnostic logic only. It does not validate behavior on console hardware.

## Remaining launch requirements

1. Obtain trusted retail 14.02 values for the syscall entries and handler
   prologues touched by GoldHEN. The supplied reference zeroes these fields.
2. Guard and verify the loader and GoldHEN core writes in separate phases.
   The compiled candidate has 63 logical fixed write targets, including
   seven complete syscall entries and ten dynamically resolved handlers.
3. Integrate the bootstrap with explicit refusal handling, full cleanup
   verification, and diagnostic checkpoints. Review the machine code and
   failure paths independently.
4. Perform a controlled kernel-only test and cleanup before attempting a
   GoldHEN thread. Keep the 14.02 launch disabled until those checks pass.

Local offline checks:

```sh
node tests/preflight-1402-selftest.cjs
node tests/guarded-bootstrap-1402-selftest.cjs
node tests/teardown-verify-1402-selftest.cjs
```
