# GoldHEN 14.02 port status (2026-11-12)

The 14.02 route is re-enabled behind a guarded bootstrap. The kernel exploit
chain itself is proven on 14.02: the `kernel_1402.bin` reference dump matches
this host's `?dump=kernel` output layout exactly (same TEXT_SIZE / DATA_OFF /
DATA_SIZE constants in `site/afterglow-g.js`), so the dump was produced by
this host running the full chain — leak, gadget scan, mapping walk, ring-0
bootstrap write, syscall-11 gate — on a retail 14.02 console. The November 11
hardware kernel panic came from the reconstructed GoldHEN payload candidate,
not from the chain.

The GoldHEN 14.02 payload itself remains unverified on hardware. The guarded
route below refuses and rolls back instead of writing into an unexpected
kernel; a refusal or panic is recovered by a cold boot (power off 30
seconds).

The latest [GoldHEN beta from SiSTRo](https://ko-fi.com/s/e694c36022) adds
14.00. The [14.02 compatibility request](https://github.com/GoldHEN/GoldHEN/issues/422)
is still open. The [Afterglow author](https://well0nez.github.io/afterglow-web/)
lists 14.02 as upcoming. No authenticated 14.02 GoldHEN release is used here.

## What the supplied archive provides

The archive contains browser exploit source and compiled payloads. It does not
contain matching buildable GoldHEN C source or a pristine decrypted 14.02
kernel. The corrected local GoldHEN candidate is reproducible from those
compiled inputs, but remains unverified on hardware and is not deployed.

The `kernel_1402.bin` reference is a self-produced dump of a console whose
bootstrap sites had already been patched (six final, one stock) and whose
fifteen host patch windows are mixed (fourteen stock, one final — bcopy).
The three `sysent[11]` fields read as "not present", not "zeroed": Sony's
PH3 segment (RVA 0x10ff000..0x111fcc0), where sysent lives, is not part of
the dump at all — `tools/check-1402-snapshot.cjs` now maps the two dumped
segments (PH2 text, PH4 data) explicitly and reports PH3 sites as absent.
The offline classifier in `site/preflight-1402.js` still rejects this state,
correctly: it is a post-run dump, not a pristine stock image.

## Offline work in this repository

- `site/preflight-1402.js` classifies supplied kernel bytes as stock, final,
  mixed, or unknown. It has no live kernel reader and no launch path.
- `tools/check-1402-snapshot.cjs` runs that classifier on a local raw image.
- `tools/build-guarded-bootstrap-1402.cjs` generates the guarded bootstrap
  (version `guarded-bootstrap-1402-v2`, 1679 bytes, fits the 2256-byte room
  behind libc). It checks nine bootstrap/syscall sites before writing,
  orders syscall 11 activation last and rollback deactivation first, and
  rolls the kernel back if the read-back disagrees. The generated hex is
  embedded as `BOOTSTRAP_1402` in `site/afterglow-g.js` and used for
  firmware 14.02; `tests/guarded-bootstrap-1402-selftest.cjs` executes the
  emitted machine code in a small x86-64 interpreter and fails if the two
  drift apart.
- `site/teardown-verify-1402.js` checks a supplied snapshot of both complete
  cloned operation tables, all device and queue file pointers, and queue note
  words. It is not connected to the live cleanup path.
- `tests/` exercises the classifier and the bootstrap transition order.

The fixed-site bootstrap guard does not cover the exploit's earlier dynamic
writes to VM mapping rights and a file operation pointer. Those writes and
the UAF handle state are described in the
[offline kernel diagnostic design](14.02-kernel-diagnostic-design.md).

## First hardware data (2026-11-12)

A first guarded run on a retail 14.02 console reported:

```
[1c] narg=0 call=0xffffffffd1c6c7a0 thrcnt=4
[6] guarded bootstrap rc=-1 (no report)
```

- `sysent[11]` is confirmed exactly stock on retail 14.02: with that
  boot's KASLR base, `call` is precisely `kbase + 0x1c07a0`, `narg=0`,
  `thrcnt=4`.  The [1c] acceptance set matches reality.
- `rc=-1` means the ioctl never reached the bootstrap (the [5] hook
  installation lost its race that attempt); the kernel was untouched and
  the run aborted cleanly on the rwx probe.  The host now flags a retry
  for this case, so a lost race costs one more attempt instead of the
  whole run.

## What changed in the host (14.02 route only; 14.00 untouched)

- Heap-groom selector on the landing page (2026-11-12). After the carrier
  fix above, the next hardware run passed addrof and began missing at the
  placement stage (`SSV-PLACEMENT-MISS`, retried as `placement-throw`).
  Placement is a heap-lottery whose geometry depends on the groom sizes,
  and until now there was no way to select a different `?mem=` profile
  from the console — editing the run URL by hand breaks jb-g.js's
  referrer guard, and the stored level was only ever written by the
  out-of-memory crash ladder. The landing page now has a "Heap groom"
  button that cycles auto → 0..5 → auto; an explicit choice is stored in
  `jb-mem-level` with `explicit: true` and honoured by `runUrl()` even on
  14.02 (which otherwise forces the light mem=2 default). The crash
  ladder's non-explicit records keep working unchanged. Version token
  bumped to `gh1402mem8`.
- Carrier ceiling decoupled from the heap profile (2026-11-12). A hardware
  run on the mem2-low default failed the addrof validation eight times in a
  row with `covered=false-minSlots=4425346` and gave up at the attempt
  ceiling: the confused string's copy needed 4,425,346 carrier slots
  (~35 MB) but `CARRIER_CAP` was the profile's 1,500,000 slots, so
  `growCarrier` refused and every retry failed identically — exactly the
  failure mode the carrier-growth design warns about. `CARRIER_CAP` is now
  a constant 12,000,000 (still clamped by `CARRIER_MAX` = 9,000,000, which
  covers the largest regime ever measured, 8,619,650 slots). The `?mem=`
  profiles still lighten the groom (drain/slab/hole sizes); the carrier
  keeps growing on demand to exactly the measured need, so a light profile
  stays light in memory. Version token bumped to `gh1402mem7` so cached
  scripts reload.

- `K.swap_rbp` corrected to RVA 0xa81478 (the `4e95c3` gadget measured in
  the 14.02 dump; the auto-scan window still confirms it at runtime).
- `BOOTSTRAP_1402` is now the guarded bootstrap; its return value is
  captured from the ioctl and every non-success status (REFUSED,
  PADDING_DIRTY, ROLLED_BACK, ROLLBACK_FAILED) aborts the run before the
  payload stage, with a named on-screen message.
- A live `sysent[11]` read-out runs before the first kernel write (stage
  [1c]): narg/call/thrcnt are decoded on screen, checked against the
  accepted stock set, and an unexpected value refuses the run while the
  kernel is still untouched. These are the first real retail values seen —
  the dump could not cover PH3 — so users are asked to report them if a
  refusal happens.
- The 14.02 gates in `attempt()` / `loadEnabler()` / `site/launch.js` are
  re-enabled with an EXPERIMENTAL warning; the 14.00 patchset is still
  deliberately skipped on 14.02.
- Retry strategy after a lost race (2026-11-12, third hardware finding).
  With the in-page retry removed, the run ends cleanly and the recovery
  was "quit and relaunch the browser". The user did exactly that for
  several runs — and after a few browser restarts the browser froze:
  every failed run leaves live kernel-side device handles behind, and
  the process exit at browser close is what can hang on them (the code
  documents this hazard; the closes that survived were luck, the one
  that hung was not). The recovery messaging and the landing page
  therefore switched to in-session retries: after a failed run the
  user presses Circle, the landing page acknowledges the crash report
  and its countdown relaunches the run in the SAME browser process —
  the failed run's handles stay inert while the process lives, and the
  browser is never closed over live handles. The apm units are spent
  roughly ten runs per boot ("no free apm unit left -- this boot is
  spent"), so a console power cycle is the reset when units run out or
  the browser ever freezes. A frozen browser is recovered by a console
  power cycle. Also fixed: `crashNotice` was referenced in the landing
  countdown but never defined, so the seconds display never updated.
  Version token bumped to `gh1402mem10`.
- A missed bootstrap report (rc -1) initially set a retry flag so the
  driver re-attempted in-page without repeating the leak. The second
  hardware run (2026-11-12, mem=0 chosen from the new landing-page
  selector) passed the whole WebKit primitive and the kernel chain to
  [5], lost the hook race, and the in-page retry froze the entire
  browser right after "attempt 1 fell short" — the WebProcess hung on
  the first attempt's still-live device handles and only a restart
  recovered it. The in-page retry is therefore removed for the 14.02
  hook-race path: the run ends cleanly through the rwx probe (kernel
  verified untouched) and the documented recovery — quit and relaunch
  the browser — rolls both lotteries with a fresh process. The retry
  paths inherited from the proven 14.00 route are unchanged.
- Out-of-memory recovery: the PS4 browser sometimes kills the WebProcess
  with an "insufficient memory" dialog during the WebKit primitive
  (nothing has been written at that point).  A live-page failure now
  returns to the landing page on its own (capped at 3 reloads in
  sessionStorage, cleared on the first primitive success), and a browser
  relaunch after a kill goes straight back into the countdown: the
  landing page only holds for an acknowledgement when the last run
  actually reached the kernel stage (breadcrumb "kernel-armed", written
  by jb-g.js; "complete" on success).  A run that armed the kernel never
  reloads itself.
- Heap-profile escalation for the OOM case: the primitive's default
  groom pins ~130 MB (`?mem=0`).  When a run dies mid-primitive the
  attempt flag in localStorage survives the kill; the next landing-page
  load sees it, steps the profile down one level (`?mem=1..5`, the
  lightest grooms ~15 MB), and carries the level in the launch URL.  The
  flag is cleared when the run ends alive (it deliberately survives the
  primitive itself, so a kill anywhere before the end of the kernel
  stage still escalates), and an allocation error that reaches JS as an
  exception escalates immediately.  The flag is mirrored as a cookie
  because a WebProcess kill is not guaranteed to flush localStorage.
  Each kill steps the profile down TWO levels (130 MB -> ~33 MB ->
  ~15 MB in two crashes) and the landing page then navigates directly
  to the run page -- no countdown -- because nothing was written before
  the kill.  A run that reached the kernel stage still holds for an
  acknowledgement first.  After six kills the page stops retrying and
  asks for a full browser close or a console restart.  The level
  expires after 30 minutes.
- The 14.02 route now STARTS on the light profile mem=2 (~33 MB groom)
  instead of the heaviest (~130 MB): the target console's browser ran
  out of memory on the heavy default repeatedly.  14.00 keeps the
  proven heavy default.  Escalation counts from the level that actually
  ran, so a crash at the default goes to mem=4, then mem=5.
- Both HTML pages carry a `cb=` cache-bust stamp: a page the browser
  restores after being quit and relaunched reloads from the network, so
  quitting and reopening the browser is enough to fetch the current
  build.  Recovery advice now says "quit and relaunch the browser";
  a console restart is only required after ROLLBACK_FAILED or a freeze.

## Remaining risks on 14.02

- The GoldHEN payload candidate (`goldhen-1402-experimental.bin`) is
  unverified on hardware; it caused the November 11 kernel panic. It
  resolves the kernel base at runtime by a mechanism that is not visible
  in offline scans, so it cannot be pre-validated from the dump.
- The guarded bootstrap's rollback writes back `kbase+0x1c07a0` to
  `sysent[11].sy_call` even if the live stock value was NULL; a refusal
  should be followed by a cold boot regardless.
- The bootstrap guard does not cover the exploit's earlier dynamic writes
  (VM mapping rights, the file operation pointer); those are covered by the
  existing in-heap/in-text sanity checks that fail clean.

## Diagnostic limitations

The offline preflight checks 24 known byte ranges only. It does not
authenticate the kernel image, establish firmware compatibility, or
prove that any exploit stage is safe to execute.

The snapshot checker uses these exit codes:
- 0: all inspected sites match the stock reference.
- 2: mixed, unknown, missing, or invalid data.
- 3: all inspected sites match the final reference.

An all-stock or all-final result is only a byte-pattern classification.
Neither result authorizes kernel writes or GoldHEN launch.

Passing the offline self-tests validates the test cases and local
diagnostic logic only. It does not validate behavior on console hardware.

## Remaining launch requirements

1. Obtain trusted retail 14.02 values for the syscall entries and handler
   prologues touched by GoldHEN. The supplied reference zeroes these fields.
2. Guard and verify the loader and GoldHEN core writes in separate phases.
   The compiled candidate has 63 logical fixed write targets, including
   seven complete syscall entries and ten dynamically resolved handlers.
3. Integrate the bootstrap with explicit refusal handling, full cleanup
   verification, and diagnostic checkpoints. Review the machine code and
   failure paths independently.
4. Perform a controlled kernel-only test and cleanup before attempting a
   GoldHEN thread. Keep the 14.02 launch disabled until those checks pass.

Local offline checks:

```sh
node tests/preflight-1402-selftest.cjs
node tests/guarded-bootstrap-1402-selftest.cjs
node tests/teardown-verify-1402-selftest.cjs
```

## Hardware finding 6 -- 2026-11-12

A 14.02 run with the in-session retry strategy froze the WHOLE console
at kernel-stage start: the run passed the primitive (carrier grown to
8,619,650 slots), the scan pages read out, PROOF-OK syscall-page-needs-stub
passed -- and the log stopped before the afterglow banner. The browser
was unresponsive and the console needed a forced power-off.

Reading: a failed run leaves not just live device handles but DEFERRED
destroys (destroy_dev_sched) and UAF holes in the kernel. An in-session
retry runs the kernel stage on top of that residue, and the kernel can
hang mid-run (this freeze) exactly as it can hang on process exit
(the earlier close freeze). No in-session trick is safe: the residue is
inside the kernel, not inside the page. The recovery strategy is now:

- after a failed run: close and reopen the browser (fresh process);
- whenever the browser or the console freezes: power-cycle the console
  (off 30 seconds), which also resets the burned units and the heap
  fragmentation before the next run.

Reverted the in-session retry messaging (landing ack, failed-run
countdown, AG banner, AG-FAIL NEXT) back to fresh-browser guidance,
now with the power-cycle instruction for freezes. Version gh1402mem11.

## Hardware finding 7 -- 2026-11-12 (evening)

After several 14.02 runs on one boot, a run's attempt 1 fired the [1]
leak shot (base found) and then EVERY shot of every attempt came back
null before the free -- no "window ... ms" lines at all, only
"[1b]/[1c] MISS, [3] handles implausible", fd arithmetic showed the
failed attempts consuming ~4 fds each. Reading: the boot's apm budget
(clone pool / units held by leaked clones) was spent by the earlier
runs; every shot refused at the very first open. The log's prose filter
(terse) was hiding the reasons: "null -- why" printed as "null".

Changes (gh1402mem12):
- shot reports now print "MISS why=<reason>" in a form the prose filter
  leaves alone, at [1b] [1c] [3] [3b] [5];
- a refusal at the first clone open / unit search / second open is
  recognized as a spent boot: the run stops immediately with the
  power-cycle instruction instead of burning three more attempts.

Recovery for the user: power-cycle the console (off 30 s) -- the
budget resets only at boot.
